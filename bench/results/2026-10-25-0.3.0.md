# datumesh-engine 0.3.0 benchmark, 2026-10-25

Same host, database and command as `2026-10-24-0.2.0.md` (0.2.0); datumesh-store 0.3.1,
datumesh-core 0.3.4. One call at a time from one thread. The development host was shared
with other work during the run; differences within about 20% are noise.

Against 0.2.0: the rows without slices read the same queries as before; the by-reference
and validated rows are within noise. The rows that evaluate (cold first ever 5.53 -> 6.6 ms,
diamond 19.8 -> 28.5 ms, 1,000-deep chain 4.53 -> 5.6 s, graph build 50 -> 58 s, the
propagating correction 27.1 -> 29.4 s) are 10-40% slower, beyond noise for the diamond. No query was added on
these paths; the likely cost is in memory (each frame carries its asof, answers are kept by
(asof, cell id), every attempt opens and closes a budget meter). Not profiled.

Slices: 101,000 stored cells of a function m(g, k): g = 0 with 1,000 cells, g = 1 with
100,000. total(g) sums m(g, *). "Cold" is the first request ever: `slice_members` as of A,
`slice_members` as of the end of time (to know whether the answer holds after A, for the
memo), each member's receipt parsed, the manifest built and stored (`put_manifest`), the
receipt signed and stored. "Fresh engine" validates the stored version: its manifest, the
slice read again (both queries), members hash compared. "After one member's correction":
the reader is dropped by pattern and rechecked (the slice read again, both queries), then
recomputed and a new manifest and receipt stored. The computed slice is sq(n) over the
extent 1..1000: 1,000 member cells evaluated, signed and stored in the cold row.
