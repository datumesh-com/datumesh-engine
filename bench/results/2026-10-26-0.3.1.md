# datumesh-engine 0.3.1 benchmark, 2026-10-26

The development host was **not quiet** during these runs: other agents' builds and tests ran
in parallel all evening (load average 4-9 on 6 vCPU; it never fell below 1 in two hours of
waiting). To make the comparison fair anyway, the early-cutoff case is measured by
`examples/cutoff.rs` (the benchmark's case alone, repeated), with 0.2.0, 0.3.0 and 0.3.1 run
interleaved, twice per session, in two sessions; the same source file is compiled against
each release (0.2.0 and 0.3.0 from their tags, on their locked dependencies; 0.3.1 on store
0.3.2).

## The early-cutoff regression

A correction of s(10000) by +2 under the 10,000-cell graph: g(0, 0)'s value (a parity) does not
change, about 5,000 answers above it are dropped and rechecked from memory. Time from the new
version to the correct answer at the top, p50 (mean) in ms:

| Pass | 0.2.0 | 0.3.0 | 0.3.1 |
|---|---:|---:|---:|
| 1 (30 rounds) | 164.0 (167.0) | 286.0 (280.5) | 190.3 (189.2) |
| 2 (30 rounds) | 177.8 (175.3) | 287.9 (286.7) | 202.3 (205.7) |
| 3 (60 rounds) | 207.6 (206.7) | 329.2 (328.6) | 211.5 (212.6) |
| 4 (60 rounds) | 199.2 (200.6) | 282.7 (288.0) | 226.3 (223.5) |

0.3.0 was 62% slower than 0.2.0 here (about the 170 -> 257 ms of the 1.3 report on a quieter
host); 0.3.1 is 11% slower on average (2% to 16% per pass).

**Where it went (perf, `--call-graph dwarf`, the rounds only, in a privileged container).**
In 0.3.0, `FunctionDescriptor::hash` (JCS + SHA-256 of the descriptor) took 15.4% of the
rounds' samples: the engine asked the runtime `asof_dependent(descriptor)` for every frame
(in `kept`, `store_frame` and `eval_frame`), and the native test runtime answers by hashing the
descriptor to look it up. The formula runtime answers by parsing the body's canonical AST,
which costs more still. 0.3.1 asks once per function hash (a cache beside the descriptors').
The rest of 0.3.0's extra time was allocation: two `String` keys built for every lookup of an
answer `(asof, cell id)` and of a binding `(name, instant)`, and a new name map for every
answer. 0.3.1 looks both up by `&str` in nested maps and shares an input's name map when
nothing is added.

**What remains (about 11%).** In 0.3.1's profile the shares are those of 0.2.0's: allocation
and freeing (malloc, free and libc's internals: the largest share in both), `Memo::end`
(24% in both), dropping the replaced answers (14% vs 16%), `check_use` (5% vs 6%). What is
new per answer: names keyed by (name, transaction time), the frame's asof carried and
compared, the inputs' kinds (cell or slice), the memo flag, and `facts`/`kept` (4% and 3%),
which build the answer from those. That is the bookkeeping of transaction-time reads, slices
and asof-dependence; I did not find a single cause left to remove.

Slice reads (0.3.1 on store 0.3.2 against 0.3.0 on store 0.3.1, the 2026-10-25 run): a sum
over 100,000 stored members cold 22.9 -> 13.0 s, validated by a fresh engine 20.3 -> 7.9 s,
after one member's correction 29.0 -> 16.3 s; over 1,000: 432 -> 339 ms, 278 -> 123 ms,
252 -> 191 ms. No receipt bytes are read for the members (`slice_values`) and the second scan
is one indexed query (`slice_changed_after`).

## The benchmark, back to back

`examples/bench.rs` of each release, one after the other (0.2.0 then 0.3.1), same session.
Single-sample rows (the graph's corrections) are noisy under this load; read them against the
interleaved table above. Rows that only time the core and the store (signing, `put_receipt`)
moved too: 206 -> 256 µs and 2.20 -> 3.12 ms, with code that did not change in the engine
(store 0.3.2's `put_receipt` also fills its new value column).
